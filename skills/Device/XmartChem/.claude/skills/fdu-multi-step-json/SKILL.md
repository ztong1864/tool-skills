# fdu-multi-step-json

## 功能

将多个实验方案文件分别转换为 step JSON，并合并成一个总 step JSON。

## 强制执行顺序

1. 使用 `python scripts/generate_multi_step_json.py --plan-files <file1.md> <file2.md> ... --output <输出文件>`。在 LabOntology 中 `--output` 写 mission 的 artifacts 目录下的文件（例如 `<artifacts 目录>/generated_multi_step_json.json`）；不带 `--output` 时会写进本技能目录的 `output/`，那是所有用户共用的目录，服务器上可能不可写。
2. **这一步很慢，必须把命令的超时设足**：每份方案要调一次模型，正常 25-60 秒一份，10 份方案要 5-10 分钟。用 Bash 工具执行时 `timeout` 至少给 `900000`（15 分钟），不要用默认值；给得不够会在中途被掐断，白跑已经转换好的那几份。
3. 对每个方案文件单独调用一次 `fdu-step-json`。
4. 按当前实现的合并规则拼接各组步骤，并重新整理 `step_index`。
5. 如提供 `--target-layout-codes`，其数量必须与方案文件数量一致。
6. 中途失败（模型服务异常、命令超时被掐断）时**原样重跑同一条命令**：已经转换好的方案从缓存里取，只补还缺的那几份。重试时换个 `--output` 文件名没关系（缓存按方案正文算，同一目录下照样命中）；但不要把 `--output` 换到另一个目录，那会另起一个缓存目录、10 份全部重做。

## 输入输出

- 输入：一个或多个 `.md` 方案文件，可选 `--target-layout-codes` 和 `--task-name`。
- 输出：`--output` 指定的文件；不带 `--output` 时为 `output/generated_multi_step_json_<timestamp>.json`。
- 缓存：单份方案转换好的 step JSON 写在 `--output` 同级的 `step_json_cache/`（可用 `--cache-dir` 指定，`--no-cache` 关闭），按方案正文的摘要命名。方案改过就会重新转换，不会拿旧结果顶上；合并成功后这个目录可以删。
- 约束：输出为合并后的总 step JSON，必要时保留 `task_name`。

## 注意事项

- 各方案内部顺序应保持不变。
- 各组的步骤不必完全相同：一组推荐条件可能少一项物料或少一步（例如不加分子筛，或某份方案没有单独的冷却步骤）。各组的反应控制和过滤步骤按顺序和反应控制条件（温度、时长、转速）对齐到同一行，某组缺少的步骤在它的反应位上留空，其余步骤照常排进总表；脚本输出一行“提示：……”说明哪组缺了哪一步。合并不会因此失败，把提示转告用户即可，不要为了让各组一致而重跑方案或手改 JSON。
- 方案文件缺失、内容为空或下游生成失败时应直接失败。
- 目标位覆盖时，相关布局字段应保持一致。
- 每个方案文件在调用下游 `fdu-step-json` 时存在固定超时限制（11 分钟，够它内部重试完），超时应视为失败。
- 模型服务抖动（连接被断开、返回 429/502/503/504、读超时内一个字节都没回）由 `fdu-step-json` 自己重试 3 次，三次都失败才算这份方案失败。失败信息里会带上是哪一类异常，照实转告，不要替它改写成“接口未配置”之类的结论。
- 每个方案的 `fdu-step-json` 结果既写进缓存目录，也不写进 `fdu-step-json` 的 `output/`（那是所有用户共用的目录）。
- 输出进度格式与 `fdu-experiment-plan` 一致，使用 `[done/total]` 标签。
